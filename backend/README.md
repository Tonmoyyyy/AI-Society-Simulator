# AI Society Simulator — Backend (Phase 1 + 2 + 3 + 4)

**Phase 1** delivers: FastAPI scaffold, MySQL connection via SQLAlchemy, Alembic
migrations, and a working JWT auth flow (signup / login / refresh / a
protected `/me` route).

**Phase 2** delivers: the `citizens` table (no money column — wallets are the
source of truth, added in Phase 5) and a full CRUD API, with randomized-but-
structured personality generation and the v0.1 100-citizen cap enforced.

**Phase 3** delivers: the simulation tick engine — `memories` and
`simulation_ticks` tables, a utility-scored decision pipeline (perceive →
score → select → execute) driving a 5-action catalog (sleep, eat, work,
socialize, create_post), and both a manual tick trigger and an optional
APScheduler background loop.

**Phase 4** delivers: the social system — `posts`, `comments`, `reactions`,
`follows` tables, a public feed API, and a realtime WebSocket feed. The tick
engine's `create_post` action now writes a real `posts` row (with
mood-derived template content) instead of just changing citizen state.

No economy (wallets/salary) yet — that's Phase 5.

## 1. Prerequisites

- Python 3.11+
- A running MySQL 8 server (local install or Docker container)

## 2. Setup

```bash
cd backend
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

Create your database and a dedicated user in MySQL:

```sql
CREATE DATABASE ai_society_simulator;
CREATE USER 'app_user'@'localhost' IDENTIFIED BY 'app_password';
GRANT ALL PRIVILEGES ON ai_society_simulator.* TO 'app_user'@'localhost';
FLUSH PRIVILEGES;
```

Copy the env template and fill in your real values:

```bash
cp .env.example .env
# edit .env — set DATABASE_URL to match the DB/user you just created,
# and set JWT_SECRET_KEY to a long random string
```

## 3. Run the database migration

```bash
python -m alembic upgrade head
```

This creates the `users` table (see `alembic/versions/` for the migration
file). To generate a new migration after changing a model:

```bash
python -m alembic revision --autogenerate -m "describe your change"
python -m alembic upgrade head
```

## 4. Run the app

```bash
python -m uvicorn app.main:app --reload
```

- App: http://127.0.0.1:8000
- Interactive API docs (auto-generated by FastAPI): http://127.0.0.1:8000/docs
- Health check: `GET /health`

## 5. Auth endpoints (Phase 1 scope)

| Method | Path | Auth required | Purpose |
|---|---|---|---|
| POST | `/api/v1/auth/signup` | No | Create a new user (always role=spectator in v0.1) |
| POST | `/api/v1/auth/login` | No | Returns `access_token` + `refresh_token` |
| POST | `/api/v1/auth/refresh` | No (needs refresh token in body) | Returns a new `access_token` |
| GET | `/api/v1/auth/me` | Yes (Bearer access token) | Returns the current user — proves the auth chain works |

Example (curl):

```bash
curl -X POST http://127.0.0.1:8000/api/v1/auth/signup \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"SecurePass123"}'

curl -X POST http://127.0.0.1:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"SecurePass123"}'
# → copy the access_token from the response

curl http://127.0.0.1:8000/api/v1/auth/me \
  -H "Authorization: Bearer <access_token>"
```

## 6. Citizen endpoints (Phase 2 scope)

| Method | Path | Auth required | Purpose |
|---|---|---|---|
| POST | `/api/v1/citizens` | Yes | Create a citizen. Empty body `{}` → fully randomized name/age/personality. `{"name":..,"age":..}` → seed those, personality is always generated. |
| GET | `/api/v1/citizens` | No | Paginated list (`?page=1&page_size=20`) — public/spectator read |
| GET | `/api/v1/citizens/{id}` | No | Single citizen detail |
| PATCH | `/api/v1/citizens/{id}` | Yes | Update `name`, `job`, or `current_activity`. Personality is not editable — it's fixed at creation. |
| DELETE | `/api/v1/citizens/{id}` | Yes | Remove a citizen |

Notes:
- **v0.1 cap:** creation returns `409 Conflict` once the citizen count hits `MAX_CITIZENS_V0` (100, set in `app/core/config.py`).
- **personality_json** is a flat dict of five 0–100 int traits (`kindness`, `intelligence`, `ambition`, `social`, `honesty`), drawn from a normal distribution centered at 50 — see `app/simulation/personality.py`.
- **No money field on citizens** — that's intentional per the approved schema; wallets (Phase 5) are the only source of truth for money.
- Create/update/delete require a Bearer token (any logged-in user, not just admin, for v0.1); list/get are public so spectators can browse without an account.

Example:
```bash
curl -X POST http://127.0.0.1:8000/api/v1/citizens \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{}'
```

## 7. Simulation endpoints (Phase 3 scope)

| Method | Path | Auth required | Purpose |
|---|---|---|---|
| POST | `/api/v1/simulation/tick` | Yes | Manually runs one tick — every citizen perceives their state, picks the highest-utility action, and executes it |
| GET | `/api/v1/simulation/ticks` | No | Tick history (most recent first) — `id`, `tick_number`, timing, `citizens_processed`, `status` |
| POST | `/api/v1/simulation/scheduler/start` | Yes | Starts the background APScheduler loop (one tick every `TICK_INTERVAL_SECONDS`, default 10s dev / config in `app/core/config.py`) |
| POST | `/api/v1/simulation/scheduler/stop` | Yes | Stops the background loop |
| GET | `/api/v1/simulation/scheduler/status` | No | `{"running": true/false}` |
| GET | `/api/v1/citizens/{id}/memories` | No | A citizen's memory log, most recent first |

**How a tick works** (`app/simulation/decision_pipeline.py` + `app/simulation/actions.py`):
1. **Perceive** — the citizen's current DB row *is* the perception (no separate gather step at this scale).
2. **Generate candidates** — each action's `is_valid()` filters out actions that don't make sense right now (e.g. `work` requires a real job and enough energy).
3. **Score** — each valid action's `utility()` combines personality traits + current needs (e.g. `sleep` utility rises as `energy` falls; `work` utility rises with `ambition`).
4. **Select** — highest score wins; a small personality-scaled noise term breaks ties without making the choice pure random.
5. **Execute** — mutates the citizen's `mood`/`happiness`/`energy`/`health`/`current_activity`, and — for `work`/`socialize`/`create_post` only — writes a `memories` row. Routine actions (`sleep`, `eat`) intentionally don't log memories; only "notable" ones do.

**Important design notes / assumptions:**
- **`mood` is on a -1.0 to 1.0 scale**, unlike `happiness`/`energy`/`health` which are 0-100. This follows the original full design doc's spec for mood specifically; flagging it since it's easy to assume all four stats share one scale.
- The tick engine does **one batch commit per tick**, not one commit per citizen (per the SDD's performance guidance) — if a tick fails partway, it rolls back cleanly and the `simulation_ticks` row is marked `"failed"`.
- No cross-citizen conflict resolution yet — every v0.1 action is single-citizen. That logic arrives with Phase 4's social interactions.
- The scheduler does **not** auto-start when the app boots — it's opt-in via the `/scheduler/start` endpoint. This keeps `pytest` (and casual API use) from silently running background ticks against your real database.

Example — run one tick by hand and inspect a citizen's memories:
```bash
curl -X POST http://127.0.0.1:8000/api/v1/simulation/tick -H "Authorization: Bearer <token>"
curl http://127.0.0.1:8000/api/v1/citizens/1/memories
```

## 8. Social endpoints (Phase 4 scope)

| Method | Path | Auth required | Purpose |
|---|---|---|---|
| POST | `/api/v1/citizens/{citizen_id}/posts` | Yes | Manually create a post as a citizen (primary path is the tick engine's `create_post` action — see below) |
| GET | `/api/v1/feed` | No | Paginated feed, newest first, with `citizen_name`, `comment_count`, `reaction_count` |
| POST | `/api/v1/posts/{post_id}/comments` | Yes | `{"citizen_id": ..., "content": ...}` — comment as a given citizen |
| GET | `/api/v1/posts/{post_id}/comments` | No | List comments on a post |
| POST | `/api/v1/posts/{post_id}/reactions` | Yes | `{"citizen_id": ..., "type": "like"}` — one reaction per citizen per post (`409` on duplicate) |
| DELETE | `/api/v1/posts/{post_id}/reactions/{citizen_id}` | Yes | Remove a citizen's reaction |
| POST | `/api/v1/citizens/{citizen_id}/follow/{target_id}` | Yes | Follow another citizen (`400` on self-follow, `409` on duplicate) |
| DELETE | `/api/v1/citizens/{citizen_id}/follow/{target_id}` | Yes | Unfollow |
| GET | `/api/v1/citizens/{citizen_id}/followers` | No | Who follows this citizen |
| GET | `/api/v1/citizens/{citizen_id}/following` | No | Who this citizen follows |
| WS | `/ws/feed` | No | Realtime feed — pushes `{"type": "new_post" \| "new_comment", ...}` as they happen |

**How posts get created:** the tick engine's `create_post` action (in
`app/simulation/engine.py`) generates mood-derived template content
(`app/simulation/post_content.py`) and writes a real `posts` row in the same
batch commit as the rest of the tick — no separate transaction. The manual
`POST /citizens/{id}/posts` endpoint exists for testing/seeding, same pattern
as citizen create/update in Phase 2.

**Realtime feed:** both the manual post/comment endpoints and tick-generated
posts broadcast over `/ws/feed`. Since neither FastAPI's sync route handlers
nor the APScheduler tick job run on the main asyncio event loop, broadcasts
go through `asyncio.run_coroutine_threadsafe` (see
`app/websocket/connection_manager.py`) — this is what makes it safe to call
from both places uniformly.

**A balance bug we found and fixed:** the original `create_post` utility
score lost to `socialize` about **98.5%** of the time across random
personality draws — meaning the simulation would almost never generate its
own posts, leaving the feed essentially dead. We reweighted both actions'
utility functions (see the comments in `app/simulation/actions.py`) so
`create_post` now wins roughly 30–40% of the time, still personality-
dependent (sociable/honest citizens post more) rather than a coin flip.
`tests/test_social.py::test_create_post_and_socialize_are_both_competitive`
is a regression test for this — it fails if the balance drifts back toward
either extreme.

Example:
```bash
curl -X POST http://127.0.0.1:8000/api/v1/citizens/1/posts \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"content": "Hello world!"}'
curl http://127.0.0.1:8000/api/v1/feed
```

## 9. Run tests

```bash
python -m pytest tests/ -v
```

Tests run against an in-memory SQLite DB (not MySQL) so the suite has zero
external dependencies. This works because the code sticks to portable
SQLAlchemy types — the same models run against both engines. 57 tests total
(10 auth, 14 citizens, 15 simulation, 18 social — including a WebSocket test
using `TestClient.websocket_connect`), all passing.

## What's in Phase 1 + 2 + 3 + 4

```
backend/
  app/
    api/v1/auth.py       → signup, login, refresh, me routes
    core/
      config.py          → Settings (env-driven)
      security.py        → password hashing (argon2), JWT create/decode
      deps.py            → get_db, get_current_user, require_admin
      error_handlers.py  → consistent {error:{code,message}} responses
    db/
      base.py            → shared SQLAlchemy declarative Base
      session.py         → engine + SessionLocal
    models/
      user.py             → users table (int PK, per approved v0.1 corrections)
      citizen.py          → citizens table (no money column — see Phase 2 notes)
    schemas/               → Pydantic request/response models
    repositories/
      user_repo.py        → DB access only, no business rules
      citizen_repo.py     → DB access only, no business rules
    services/
      auth_service.py     → signup/login/refresh business logic
      citizen_service.py  → citizen CRUD + v0.1 100-citizen cap enforcement
    simulation/
      personality.py      → personality_json generator (5 traits, 0-100)
      name_generator.py   → random name generator for auto-created citizens
      actions.py          → the v0.1 action catalog (sleep/eat/work/socialize/create_post): is_valid/utility/execute per action
      decision_pipeline.py → decide_and_act(citizen): the per-citizen perceive→score→select→execute loop
      engine.py            → run_tick(db): orchestrates decide_and_act across all citizens, batches the commit, records the tick, writes real posts + broadcasts
      post_content.py      → mood-derived template content for the create_post action
    tasks/
      tick_scheduler.py    → APScheduler background loop calling engine.run_tick() on an interval
    websocket/
      connection_manager.py → realtime feed broadcast, thread-safe for both API handlers and the scheduler thread
    main.py                → FastAPI app entrypoint (lifespan-based startup, /ws/feed route)
  alembic/                 → migrations (wired to app.core.config + models)
  tests/                   → pytest suite (57 tests, all passing)
  requirements.txt
  .env.example
```

Layering is strict: **API → Service → Repository → DB**. This is what lets
the simulation engine (Phase 3+) reuse the same services without duplicating
logic, and what makes a future MySQL → PostgreSQL move a config change
rather than a rewrite.

## Not in Phase 1 + 2 + 3 + 4 (by design)

- No wallets/salary — `work` changes mood/happiness but doesn't pay anything yet (Phase 5)
- No frontend yet (added once there's something to look at)
- `role` is always `spectator` on signup — promoting a user to `admin` is a
  manual DB update for now; an admin-management endpoint isn't needed yet
- Citizen/simulation/social write actions only require *any* logged-in user,
  not specifically `admin` — flagging this as an assumption since the SDD
  didn't specify; easy to tighten to `require_admin` later if you want that instead
- Memory has no decay/sentiment scoring yet (per the approved v0.1
  simplification) — it's a flat importance-ranked log
- No timeline/milestone-detector (SDD §9) yet — folding that into Phase 6
  alongside the dashboard, since it reads off data these phases produce
- WebSocket broadcasts are best-effort and in-memory only (no Redis pub/sub
  — per the approved v0.1 stack) — fine for one server instance, won't fan
  out across multiple processes if you ever run more than one
